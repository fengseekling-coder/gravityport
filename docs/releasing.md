# GravityPort Release Guide

This guide is for maintainers who build and publish GravityPort desktop packages. Running an installed or source copy of GravityPort is covered in [operations.md](operations.md).

## Package names

Packaging names follow the `MOSA_RELEASE_PRODUCT` switch in `scripts/release-product.mjs`: left unset it selects the GravityPort product, and setting it to `MOSA` builds the transition package that moves existing users onto the new update feed. GravityPort builds write the macOS application under `out/GravityPort-darwin-arm64/` and the Windows package directory under `out/GravityPort-win32-x64/` with `GravityPort.exe` at its root; the `MOSA` transition build uses `out/MOSA-darwin-arm64/`, `out/MOSA-win32-x64/`, and `MOSA.exe` instead. `desktop:make` packages the macOS app, creates `out/make/update/darwin/arm64/GravityPort-darwin-arm64-<version>.zip` for in-app updates, and then creates `out/make/dmg/darwin/arm64/GravityPort-darwin-arm64-<version>.dmg` for first install/manual replacement. The update-ZIP builder prints its exact byte size, SHA-256, and `platforms.macos` release-manifest patch. The DMG contains exactly `GravityPort.app` plus an `Applications` symlink, and the build verifies the mounted image before returning success. The bundle identifier (`com.azhuilab.mosa`) is stable across versions, while the app file name follows the switch; the updater accepts both `MOSA.app` and `GravityPort.app` (Windows: `MOSA.exe` / `GravityPort.exe`), so a Windows install that auto-updated from a pre-rename build keeps its `MOSA.exe` name. GravityPort Library data and Electron user-data live outside the application bundle and are not replaced by either update path.

## Distribution tracks

Desktop publishing has two explicit distribution tracks. `desktop:release` is an alias for the macOS **Preview/RC** path: it still requires clean/tagged/remote Git provenance, a pinned Ed25519 release-manifest trust root, structural package verification, packaged smoke, and a valid macOS code signature, but ad-hoc signing is allowed and Apple Developer/notarization credentials are not required. `desktop:release:production` is the separate production path; it requires Developer ID signing, Hardened Runtime, notarization, stapling, and Gatekeeper acceptance before the update ZIP or DMG is accepted. On Windows, `desktop:release:windows` is the unsigned-capable Preview portable-ZIP path, while `desktop:release:windows:production` requires Authenticode configuration and verifies every executable/native payload signer. `desktop:make*` remains the ordinary local-development packaging path.

Windows Preview builds may remain unsigned and SmartScreen may warn about an unknown publisher. Production builds require `MOSA_WINDOWS_SIGNER_THUMBPRINT` (use the 40-hex SHA-1 thumbprint; the release manifest accepts only that form) plus a supported signing source (`WINDOWS_CERTIFICATE_FILE` + `WINDOWS_CERTIFICATE_PASSWORD`, `WINDOWS_SIGN_WITH_PARAMS`, or `WINDOWS_SIGN_HOOK_MODULE_PATH`; `WINDOWS_SIGNTOOL_PATH` optionally points at a specific `signtool`). macOS Preview DMGs use the ad-hoc signing path and are not notarized; only `desktop:release:production` requires Apple Developer credentials: `MOSA_MACOS_SIGN_IDENTITY` (a Developer ID Application identity), `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, and `APPLE_TEAM_ID`. A conventional Windows installer and background login launch remain separate release work.

## In-app updates

### Windows

Packaged Windows builds support an explicit in-app update flow for portable ZIP releases. Release builds pin an Ed25519 release-manifest public key in their build identity, so the main process verifies `latest.json` before trusting any artifact hash or distribution mode. It then requires the artifact platform/architecture/filename to match the advertised release — the optional `platforms.windows.payloadExeName` (`MOSA.exe` by default, or `GravityPort.exe`) is bound to the package filename, shipping as `MOSA-` / `GravityPort-win32-x64-<version>.zip` respectively — downloads only from the fixed GravityPort origin, and verifies the declared byte size/SHA-256. The updater always installs under whichever of the two whitelisted names the running executable has (an unrecognized name stops the update), so an update whose payload ships the other name is renamed into the installed name inside the extracted payload before anything moves, keeping the install directory and every relaunch path on the current name. After the old main process exits, the detached helper also waits for residual processes whose executable still lives inside the current GravityPort install directory before attempting replacement; bounded `Move-Item` retries remain as a second defense against short antivirus/indexer handle retention. The helper itself is created with `CREATE_NO_WINDOW`, while the relaunched GravityPort GUI process uses its normal visible-window lifecycle rather than inheriting hidden-window semantics. Preview updates rely on the signed manifest plus post-launch build-identity verification. Production updates additionally require `platforms.windows.signerThumbprint` in the signed manifest and verify every `.exe`, `.dll`, and `.node` in the replacement payload against it: each file must carry a valid Authenticode signature whose thumbprint equals the pinned one, and an installed release that is already validly signed pins only the publisher subject (so a renewed certificate with a rotated thumbprint keeps updating, while a different publisher is refused); an unsigned Preview install may cross into Production once, trusted only through the signed manifest. The relaunched app must report the exact expected version, Git SHA, UI fingerprint, runtime fingerprint, and distribution before the transaction is accepted; otherwise rollback restores the previous directory.

### macOS

Packaged macOS arm64 builds use the same Settings update control and signed release-manifest trust root. The trusted main process accepts only `platforms.macos` entries whose identity is exactly `macOS` / `arm64` plus a filename bound to the optional `appName` field (`MOSA.app` by default, or `GravityPort.app`, shipping as `MOSA-` / `GravityPort-darwin-arm64-<version>.zip` respectively), downloads only from `https://mosa.azhuilab.com/downloads/`, rejects redirects, verifies declared size/SHA-256, and stages the ZIP under Electron `userData`. Preview replacements must have the expected bundle/version and pass `codesign --verify`, but do not require Developer ID or Gatekeeper acceptance. Production replacements additionally require Hardened Runtime, Gatekeeper acceptance, and a TeamIdentifier chain anchored in the signed manifest: the manifest's `platforms.macos.teamIdentifier` must match the payload, and an installed app that already carries a Developer ID team must carry the same one (an ad-hoc/preview install without a team is allowed to cross into production exactly once, via the signed manifest). The updater can replace the app under its current name or across names (`MOSA.app` → `GravityPort.app`); a cross-name update refuses to overwrite an app already present at the target location and moves the previous app to the Trash only after the replacement reports readiness, rolling the whole change back otherwise. When the running app sits in a Gatekeeper translocation path or a directory it cannot write to, update checks report `install-location-unsupported` and the UI asks the user to move the app into Applications first. The relaunched app must report the exact signed-manifest version, Git SHA, fingerprints, and distribution. Missing readiness, identity drift, an early crash, or any replacement failure restores the previous app and relaunches it automatically.

## Publishing a release

Publishing an in-app update means uploading each update ZIP byte-for-byte to `https://mosa.azhuilab.com/downloads/<filename>`, then publishing a `releases/gravityport/latest.json` generated and signed by `scripts/prepare-desktop-release-manifest.mjs` (below). Never paste the ZIP builder's `release_manifest_patch` into the feed or edit the signed file by hand: the Ed25519 signature covers the whole manifest, and the builder's patch carries no `appName`, so a GravityPort ZIP would be rejected. The update and download hosts stay on `mosa.azhuilab.com` on purpose; the user-facing download page is `https://gravityport.azhuilab.com/#download`. Clients released before the rename (up to 0.2.1-rc.34) read only the legacy `releases/latest.json` path, so that path receives exactly one more publish: the `MOSA` transition build, which reads the new `releases/gravityport/latest.json` feed from then on. After the transition build is published there, the legacy path is frozen and never receives a GravityPort release. Increment the semantic/prerelease version for every published build; update availability is version-based rather than Git-SHA-based. The `v0.2.1` tag was already spent on the pre-rename release while the 0.2.1-rc series continued past it, so the 0.2.1 final name is occupied — versioning continues from 0.3.0.

The release monitor must not construct `latest.json` with its own schema. Use `scripts/prepare-desktop-release-manifest.mjs` as the canonical manifest writer. Release builds must be created with `MOSA_RELEASE_MANIFEST_PUBLIC_KEY` (or `_FILE`) so the public Ed25519 key and key id are pinned into `web/gravityport/dist/build-identity.json`; manifest publishing separately requires `MOSA_RELEASE_MANIFEST_PRIVATE_KEY` (or `_FILE`). Keep the private key outside the repository and deployment web root. `MOSA_RELEASE_DISTRIBUTION=preview|production` is also bound into build identity and the signed manifest. Downgrading a Production install back to Preview stays blocked; Preview installs may cross into Production because that bridge is what lets existing users adopt the Developer-ID-signed release in place (the manifest's `platforms.macos.teamIdentifier`, required for production, keeps that trust anchored to the signed manifest). Pass `--mac-app-name GravityPort.app` (and, for production builds, `--mac-team-identifier <10-char id>`) to publish the renamed package. The writer computes artifact byte sizes/SHA-256 from the real files, binds Git/UI/runtime/distribution identity, preserves the current `visualPacks` declaration, signs the complete manifest, verifies its own signature with the packaged public key, and then passes it through the production parser. Every release must also come from a clean commit carrying `v<version>`, reachable from a remote branch, with the exact tag already pushed to `origin`.

User-facing release notes live in `release-notes.json` at the repository root, the single source for every surface that shows them. `unreleased` collects one short sentence per user-visible change, in Chinese and English, as changes merge; development builds show it on Settings → About as "Next version (in development)". To release: (1) move `unreleased` into a new first entry of `releases` with the exact `version` (for example `0.3.0-rc.1`) and `date` (`YYYY-MM-DD`), reset it to `"unreleased": { "zh": [], "en": [] }` (an empty `{}` is rejected), and add the matching CHANGELOG heading; (2) commit that together with the `package.json` version, tag `v<version>`, and push both the branch and the tag; (3) only then run a `desktop:release*` script, because the provenance check requires a clean, tagged, pushed commit. Each sentence is limited to 200 characters, and the manifest writer truncates each language's joined notes at 3,000 characters. Non-development builds (`MOSA_RELEASE_DISTRIBUTION=preview|production`) refuse to build without an entry for their own `package.json` version, and the About page bundles that entry so it can show what changed without going online. The manifest writer fills `notes.zh` / `notes.en` from the same entry, one `• ` line per sentence, unless `--notes-zh` / `--notes-en` are passed explicitly; `--release-notes <path>` points it at another file. Each release also gets a GitHub Release with the same notes: Release Candidates as pre-releases, final releases marked Latest.

Example for a macOS-only release while preserving the current Visual Pack declaration (notes come from `release-notes.json`):

```bash
node scripts/prepare-desktop-release-manifest.mjs \
  --version <version> \
  --previous /path/to/current/latest.json \
  --mac out/make/update/darwin/arm64/GravityPort-darwin-arm64-<version>.zip \
  --mac-app-name GravityPort.app \
  --output /path/to/staging/latest.json
```

`--mac-app-name` defaults to `MOSA.app`, which only accepts a `MOSA-darwin-arm64-<version>.zip`; pass `GravityPort.app` for GravityPort builds. Production builds also need `--mac-team-identifier <TEAMID>`. `platforms` is rebuilt only from the artifacts passed in this run (an entry in `--previous` is not carried over), so pass `--mac` and `--windows` together when both platforms ship the same version.

Windows packages must be built on Windows (the win32 Sharp and SQLite runtimes are provisioned natively), so a release-day Windows Preview ZIP comes from the **Windows Preview Release Artifact** workflow: run it from the Actions tab with the already-pushed tag and the package product (`MOSA` for the transition build, `GravityPort` otherwise); it builds with `MOSA_RELEASE_DISTRIBUTION=preview` and the pinned manifest public key (repository variable `MOSA_RELEASE_MANIFEST_PUBLIC_KEY`), checks the packaged build identity, and uploads the ZIP plus its SHA-256 as an artifact to download into `out/make/zip/win32/x64/` before publishing.

For Windows, `desktop:make:windows` and the `desktop:release:windows*` scripts write `out/make/zip/win32/x64/GravityPort-win32-x64-<version>.zip`. Upload it to `/downloads/` and pass `--windows <zip> --windows-payload-exe-name GravityPort.exe` (the default `MOSA.exe` expects a `MOSA-` filename), plus `--windows-signer-thumbprint <40-hex>` for Production.

After the feed is published, create the GitHub Release with `npm run release:github -- --version <version>`. It requires the `v<version>` tag on `origin`, takes its notes from the same `release-notes.json` entry, and derives the channel from the version alone: a version with a pre-release suffix is published as a pre-release and never Latest, a final version is marked Latest. Run it with `--dry-run` first to print the exact `gh` command and notes without changing anything; pass `--asset <path>` (repeatable) to attach files, and `--update` when the Release already exists. For the transition build, name it in the title, for example `--title "GravityPort v0.3.0-rc.1 (MOSA transition)"`.

## Optional Visual Pack publishing

Visual search model/runtime bytes are not shipped inside the core desktop package. Build one platform-specific pack per supported target and publish its directory tree under the fixed first-party origin:

```bash
node scripts/build-visual-model-pack.mjs --source <candidate-source> \
  --runtime-target darwin-arm64 \
  --output <release-root>/siglip2-base-patch16-224/<revision>/darwin-arm64
```

Use `--runtime-target win32-x64` for the Windows pack. The command prints a `release_manifest_patch.visualPacks.<target>` object containing the exact pack id/revision, total payload bytes, `model-pack.json` byte size and SHA-256, and license metadata. Upload the output directory byte-for-byte to `/downloads/visual-packs/<id>/<revision>/<target>/`, then add that entry to `visualPacks` in a copy of the current feed and pass the copy as `--previous` to the manifest writer, which carries `visualPacks` over and re-signs the manifest.

Do not publish the release-feed entry until every referenced file is already present at the fixed download origin. The desktop installer rejects arbitrary renderer-provided URLs, redirects, unsupported targets, mismatched runtime architecture, insufficient disk space, manifest/file size drift, SHA-256 drift, and packs that fail final `verifyVisualModelPack()` validation. Updates download beside the working revision and select the new revision only after verification, so a failed update does not destroy the last known-good pack.

## Optional C2PA helper pack publishing

`c2patool` is also kept outside the core desktop package. Prepare each target on a **native runner** so the preparation step can execute `c2patool -V` before accepting the binary. Supply the upstream license files together with the extracted official executable:

```bash
npm run prepare:c2pa-helper -- \
  --binary /path/to/c2patool \
  --version <upstream-version> \
  --license /path/to/LICENSE-MIT \
  --license /path/to/LICENSE-APACHE \
  --output <release-root>/c2patool/<version>/darwin-arm64
```

On Windows run the same command with the native `c2patool.exe`; the output target becomes `win32-x64`. The preparer verifies the executable's reported version, copies the executable and supplied license material, writes `helper-pack.json`, hashes every file, verifies the completed pack, and prints a `helperPacks.c2patool.<target>` release-manifest patch.

Upload the output byte-for-byte under:

`/downloads/helper-packs/c2patool/<version>/<target>/`

The canonical manifest writer does not carry `helperPacks` yet, and a hand edit would invalidate the feed signature, so helper-pack feed entries cannot be published until the writer supports them. Publish the files **before** publishing the release-feed reference. The desktop installer only accepts the signed GravityPort release feed — release-manifest signature verification is mandatory in code — and the fixed `https://mosa.azhuilab.com/downloads/helper-packs/c2patool/` origin; it rejects redirects, path traversal, unsupported targets, invalid sizes/hashes, symlinks, missing license/notice material, and packs whose final verification fails. Installation is staged beside the last working helper and swapped only after verification. The installer module (`desktop/c2pa-helper-installer.mjs`) is implemented and covered by tests, but no desktop UI entry point invokes it yet; releases must not describe helper installation as an end-user feature until that wiring ships.

The current upstream binary distribution uses a macOS universal archive and a Windows x64 MSVC archive. GravityPort does not download those GitHub archives at runtime; upstream artifacts are an input to the release-preparation pipeline only. Client machines download only the GravityPort-pinned helper pack from the first-party origin.
